# Implementation Plan: SDD Proactive Discussion

**Workspace**: `sdd-proactive-discussion` | **Date**: 2026-05-25 | **Spec**: [spec.md](spec.md)  
**Input**: Feature specification from `specs/sdd-proactive-discussion/spec.md`

---

## Summary

改变 `clarify` 和 `plan` 两个阶段的行为模式：clarify 从"列问题清单"变为"主动挖掘隐藏问题并给出推断"；plan 从"LM 单方面生成方案"变为"先讨论候选架构方案再写 plan.md"。改动范围限于两个阶段说明文件的行为协议。

---

## Key Design Decisions

### Decision 1: Clarify 的行为模式——"发现式"而非"问卷式"

- **背景**: 当前 clarify 的执行步骤是"识别不确定点 → 提出最小问题集 → 用户回答"。LM 的默认行为是把所有问题一次性列出，变成问卷。用户已经知道的东西不需要问，真正有价值的是用户没想到的。
- **选项**:
  - A: 在现有步骤中加"必须一次只问一个问题"的硬约束 — 解决了批量问题，但本质还是"问"，没有解决"挖掘隐藏问题"
  - B: 重写执行步骤为"分析 → 发现 → 呈现推断 → 请用户确认或补充" — 从根本上改变行为模式，LM 的角色从"提问者"变为"风险发现者"
- **结论**: 选择 B。clarify 的核心价值不是"问问题"，而是"确保没有遗漏"。LM 应该做分析工作，把发现呈现给用户。
- **影响**: 执行步骤需要重写；完成标准需要从"问题已回答"变为"隐藏风险已识别或确认不存在"。
- **来源**: 用户反馈——"不用强制问问题，重点在于要把隐藏的问题都找出来"

### Decision 2: Plan 的架构讨论——插入"方案对比"环节

- **背景**: 当前 plan 阶段直接从 spec 生成完整 plan.md，用户只能事后审阅。架构决策是讨论出来的，不是填表填出来的。
- **选项**:
  - A: 在 plan.md 模板中加"必须列出候选方案"字段 — 只是让 LM 自己多写一段，用户仍然没有参与讨论
  - B: 在 plan 阶段的执行步骤中，把"生成 plan.md"拆成两步："先输出候选方案讨论 → 用户确认后再生成 plan.md" — 真正让用户参与架构决策
- **结论**: 选择 B。plan 阶段的执行步骤需要明确区分"讨论阶段"和"产出阶段"。
- **影响**: plan.md 的执行步骤需要重写；需要定义"讨论阶段"的输出格式和跳过条件。
- **来源**: 用户反馈 + awesome-architecture 的架构决策方法论

### Decision 3: 跳过条件——不让小改动变重

- **背景**: 两个改进都可能让简单需求变得冗长。
- **选项**:
  - A: 每次都走完整流程，但允许用户说"跳过"
  - B: LM 自行判断是否需要深度讨论，简单需求快速通过
- **结论**: 选择 B。阶段说明中明确跳过条件，LM 判断后简短说明原因即可。
- **影响**: 两个阶段都需要保留"快速通过"路径。

## Module Design

### Module: Clarify Stage — 行为协议重写

**职责**: 把 clarify 从"问卷模式"改为"发现模式"。

**改动文件**: `skills/sdd/references/stages/clarify.md`

**新的行为协议**:

```text
核心转变：
  旧模式: 识别不确定点 → 列问题清单 → 等用户回答
  新模式: 分析 spec + 代码现状 → 主动发现隐藏问题 → 呈现推断和发现 → 请用户确认或补充

LM 的角色定位：
  不是"提问者"（interviewer）
  而是"风险发现者"（risk discoverer）

输出形式：
  不是: "请回答以下问题：1. X 是什么？2. Y 怎么处理？"
  而是: "我分析了 spec 和代码，发现以下你可能没考虑到的点：
         1. [发现] — [我的推断是 X，因为 Y] — 你确认吗？
         2. [发现] — [这里有冲突，A 和 B 矛盾] — 你倾向哪个？
         3. [发现] — [这个边界没定义，但我从代码推断是 Z] — 对吗？"

跳过条件：
  - spec 完整且 LM 没有发现隐藏问题 → 直接说明"没有发现遗漏"并进入 plan
  - 小改动 → 不进入深度分析
```

**注意事项**:

- 保留现有的"何时进入"和"回退条件"不变
- 保留架构质量门的触发条件不变
- 只改"执行原则"和"执行步骤"

### Module: Plan Stage — 架构讨论环节

**职责**: 在生成 plan.md 之前插入"候选方案讨论"环节。

**改动文件**: `skills/sdd/references/stages/plan.md`

**新的行为协议**:

```text
核心转变：
  旧模式: 读 spec → 探索代码 → 直接生成 plan.md
  新模式: 读 spec → 探索代码 → 讨论候选方案 → 用户确认 → 生成 plan.md

讨论环节的输出格式：
  "基于 spec 和代码现状，我看到以下候选方案：

   方案 A: [名称]
   - 思路: [一句话]
   - 适配: [为什么适合当前场景]
   - 代价: [放弃什么、引入什么复杂度]
   - 参考: [awesome-architecture 模式名 + URL，或 UNVERIFIED]

   方案 B: [名称]
   - 思路: [一句话]
   - 适配: [为什么适合当前场景]
   - 代价: [放弃什么、引入什么复杂度]
   - 参考: [来源]

   我倾向方案 A，因为 [理由]。你怎么看？"

讨论后：
  用户确认或修改 → LM 生成 plan.md，ADR 中记录被放弃的方案

跳过条件：
  - 需求简单，只有一个合理方案 → 说明原因后直接生成 plan.md
  - 用户明确说"你决定" → 给出推荐理由后直接生成
  - 不涉及架构选择的纯实现 → 不强制方案对比
```

**注意事项**:

- 保留现有的 subagent 派发逻辑不变
- 保留架构质量门和模式参考策略不变
- 讨论环节是在"探索"之后、"生成 plan.md"之前插入的

## Risks and Tradeoffs

- **讨论环节可能让流程变慢**: 通过跳过条件缓解；简单需求不触发讨论。
- **LM 的"发现"可能是错的**: 要求 LM 给出推断依据，用户可以否定；错误发现比遗漏好。
- **用户可能不想讨论**: 保留"你决定"快速路径；尊重用户节奏。
- **行为改变依赖 LM 遵守**: 阶段说明中的措辞必须足够具体和强制，不能只是"建议"。

---

## Verification Strategy

- 改完后用一个中等复杂度的 feature 走一遍 sdd 流程，观察 clarify 是否主动发现问题而非列问题清单
- 观察 plan 是否在生成 plan.md 前先输出候选方案讨论
- 用一个小改动走一遍，确认跳过条件生效、不会变重
