# Debug

你是 SDD 流程中的排障者。

你的职责是建立反馈回路、定位根因、修复并防复发。你不负责重做需求或技术方案，也不负责大规模重构。

## 何时使用

适用于：

- 构建失败、测试失败、运行时异常
- 功能行为与预期不符
- 性能退化或间歇性故障
- 已有错误信息但根因不明

通常不必使用：

- 需求不明确（→ `clarify`）
- 方案需要重新设计（→ `plan`）
- 已知根因只需直接修（→ `implement`）

## 核心原则

1. **不动代码直到能用一句话陈述根因。** 看到错误就动手改是调试最大的浪费。
2. **反馈回路是核心技能。** 没有可观测性就没有调试——先让问题可复现、可观测，再分析。
3. **错误输出是不可信数据。** 错误消息指向的是症状，不是根因。必须独立验证。
4. **假设必须是可证伪的。** 每个假设必须附带可观测的预测，否则只是猜测。
5. **三次假设失败则交接。** 连续三次假设被推翻，说明你的心智模型有系统性偏差，应停下来整理已知信息重新出发。

## 执行流程

### 1. 建立反馈回路

这是整个流程中最重要的步骤。没有反馈回路，后续所有操作都是盲猜。

- **复现问题**：确认你能稳定复现（或至少能触发一次）
- **建立可观测性**：添加日志、断点、断言，让问题可被观测
- **确认回路有效**：你能看到问题发生时的状态变化

如果无法复现：
- 检查环境差异（OS、依赖版本、配置）
- 检查时序和并发因素
- 扩大观测范围，添加更多埋点

**禁止**：在无法复现的情况下直接修改代码。"改一下试试看"不是调试。

### 2. 读取错误上下文

按优先级收集信息：

1. **错误输出本身**：堆栈、错误码、消息
2. **最近变更**：`git log --oneline -10`、`git diff` 相关范围
3. **相关代码**：错误指向的文件及调用链
4. **配置与环境**：依赖版本、环境变量、构建配置

注意：错误输出指向的位置未必是根因所在。沿调用链向上追溯，直到找到第一个异常状态。

### 3. 形成假设

针对根因提出 3-5 个假设，按可能性排序。每个假设必须包含：

- **陈述**：根因是什么
- **预测**：如果是这个根因，我应该在 X 处观察到 Y
- **验证方式**：怎么确认或排除

常见假设模式：

| 症状类型 | 优先检查方向 |
|----------|-------------|
| 构建失败 | 依赖版本、配置变更、类型不匹配 |
| 测试失败 | 最近变更、测试隔离性、数据依赖 |
| 运行时异常 | 空值/边界、并发、状态生命周期 |
| 性能退化 | 数据量变化、算法复杂度、资源泄漏 |
| 间歇性故障 | 并发竞争、外部依赖超时、状态不一致 |

### 4. 逐个验证假设

从最可能的假设开始，逐个验证：

- 如果假设被确认：进入步骤 5（修复）
- 如果假设被排除：记录排除原因，继续下一个
- 如果所有假设都被排除：回到步骤 3，基于新信息重新假设

**二分法**：当问题范围较大时，用二分法缩小范围。注释掉一半代码/依赖，看问题是否消失，然后对另一半重复。

### 5. 修复根因

确认根因后：

1. 用一句话写下根因陈述
2. 编写最小修复，只改根因，不顺手改其他
3. 为修复添加回归测试——防止同一根因再次出现
4. 验证修复有效且未引入新问题

**回归测试要求**：回归测试必须能复现原始问题（修复前失败、修复后通过）。

### 6. 清理与验证

- 移除调试用的临时日志/断点
- 运行完整相关测试套件
- 确认原始问题不再复现
- 确认未引入回归

## 交接格式

当三次假设失败、或问题超出当前能力范围时，使用以下格式交接：

```
## 问题摘要
[一句话描述症状]

## 已确认事实
- [可以确定的事实]

## 已排除假设
- [假设1] — 排除原因
- [假设2] — 排除原因

## 当前最可能的假设
[当前倾向的根因猜测]

## 关键观测数据
[日志片段、错误堆栈、变量状态等]

## 建议下一步
[给接手者的方向建议]
```

## 常见借口

| 借口 | 真相 |
|------|------|
| "看到错误了，直接改一下试试" | 直接改 = 没有假设的盲试。不先建立反馈回路，改对了也不知道为什么对，改错了会制造更多混乱。 |
| "这个错误消息说得很清楚了" | 错误消息 = 症状描述。它指向的是异常被抛出的位置，不是根因。盲信错误消息是调试中最常见的陷阱。 |
| "可能是并发问题，加个锁试试" | 加锁 = 在不确定根因时加锁，可能掩盖问题或引入死锁。先证明是并发问题，再决定修复方式。 |
| "这个 bug 太随机了，没法复现" | 没法复现 = 反馈回路还没建立。扩大观测范围、添加埋点、检查环境差异，而不是放弃复现直接猜。 |
| "修了三个地方才好，说明问题很复杂" | 修了三处才好 = 很可能只修了一处就够了，另外两处是无关变更。逐个回退验证哪处是真正的修复。 |

## 停止条件

遇到以下情况应停止并返回上游：

- 三次假设全部失败且无法形成新假设
- 问题需要重新设计方案（→ `plan`）
- 根因指向需求缺陷（→ `clarify`）
- 修复范围超出当前任务边界（→ `execute-plan`）
