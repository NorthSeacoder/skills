# Architecture Quality Gate

本文件定义 `sdd` 如何在不新增公开入口的前提下，引入架构思考、成熟架构模式参考和轻量 ADR 纪律。

## 使用时机

进入 `clarify` 或 `plan` 时，若当前需求满足任一条件，应启用本 gate：

- 涉及新系统、新子系统、跨模块流程或关键边界变化
- 涉及状态、存储、异步、缓存、队列、权限、安全或外部依赖
- 涉及性能、可用性、一致性、成本、可观测性或可演进性取舍
- 用户明确希望先讨论架构、系统设计或长期演进

以下情况通常跳过完整 gate：

- 单文件、小范围、低风险修复
- 纯文案、样式或配置微调
- 已有 plan 明确覆盖架构取舍，且本次没有改变这些取舍

跳过时应简短说明原因，不把小改动强行扩成系统设计。

## Clarify Questions

只问会阻塞 `plan` 的高价值问题。能从代码、文档或现有 spec 推断的，不问。

优先检查：

- 一句话定位：这个系统或功能到底解决什么问题
- 业务范围：包含什么，不包含什么，谁依赖它
- 规模：用户量、请求量、数据量、并发量的数量级
- 读写特征：读多写少、写多读少、实时性、批处理或混合
- 一致性：哪些地方必须强一致，哪些地方可以最终一致
- 增长路径：MVP、成长期、成熟期分别会新增什么压力
- 失败代价：慢、错、丢、重复、不可用分别有什么后果
- 硬约束：时间、团队、成本、合规、既有技术栈和迁移窗口
- 质量属性：性能、可用性、持久性、可扩展性、一致性、安全性、成本、可维护性、可观测性、可演进性

## Pattern Reference Policy

可以把成熟架构模式作为候选参考，但不能作为默认答案。

参考来源示例：

- 核心模式：分层、单体、微服务、事件驱动、消息队列/异步处理、CQRS、发布订阅、BFF、管道过滤器、微内核/插件化
- 类系统模板：普通网站、AI 对话产品、AI 网关、RAG 知识库、支付系统、实时通讯、搜索引擎、在线票务、云存储、通知系统等

引用规则：

- 必须说明当前项目阶段：MVP、成长期或成熟期
- 必须说明适配点、不适配点和放弃的替代方案
- 必须保留来源 URL
- 必须优先服从本仓库代码现实、用户目标和当前约束
- 不得因为参考模板成熟，就把成熟期架构套到 MVP

## Lightweight ADR

在 `plan.md` 中记录影响实现或维护的关键决策即可，不默认创建独立 ADR 文件。

每条关键决策至少包含：

- 背景：为什么现在必须决策
- 候选：至少两个选项或一个明确的“不做”选项
- 结论：选择什么
- 理由：为什么在当前约束下合适
- 代价：放弃什么，引入什么风险
- 来源：官方文档、外部参考 URL，或 `UNVERIFIED`

## Verify Checks

进入 `verify` 时，检查实现是否出现架构漂移：

- 是否违反 `plan.md` 中的模块边界、数据流或 ADR
- 是否新增未记录的依赖、状态、缓存、队列、外部调用或失败模式
- 关键质量属性是否有 fresh evidence
- 如果实现证明 plan 假设错误，应返回 `plan` 或 `clarify`，而不是只在实现层补丁

## Closeout Checks

进入 `closeout` 时，检查：

- 哪些 ADR 需要保留为后续维护依据
- 是否留下架构债、临时兼容或未来迁移点
- 是否需要记录架构演进触发信号，例如规模阈值、错误率、延迟、成本或人工运维负担
